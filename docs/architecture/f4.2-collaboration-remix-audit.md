# F4.2 Collaboration and Remix Audit

## Current capability model

The current course relationship model is intentionally role-independent: `courses.teacher_id` determines owner authoring capability and `enrollments` determines learning capability. An owner who is enrolled has both capabilities; no global `profiles.role` is used.

## Collaborate

There is no course-membership, collaborator, permission-grant or RLS policy surface in this repository that grants non-owner editing of an original course. The existing `requireOwner` authoring guard and source upload action correctly require `courses.teacher_id = auth.uid()`.

Adding a Collaborer button would therefore be non-functional or would require bypassing the current authorization model. It is deferred.

Minimal next-sprint proposal: a `course_collaborators` relation keyed by course and user, constrained to an explicit capability set; authoring/source RLS and server guards must accept an edit capability from that relation without using a global role. Invitation, revocation and publication permissions need separate product decisions.

## Remix

No source-lineage column, clone action, transactional copy procedure or RLS policy exists for a derived course. A Remix action cannot safely clone course, module, lesson and source relationships while retaining an immutable source reference in the current schema.

Remix is deferred rather than presented as a dead control.

Minimal next-sprint proposal: create a new owner draft plus a lineage relation/fields such as `source_course_id` and remix metadata, then clone permitted course structure under the requesting session with explicit decisions for source reuse, enrollment independence, attribution and publication.

## Decision

F4 keeps the contextual multi-capability UX (`J'apprends · Je crée`) and does not add Learner/Teacher modes. Collaborate and Remix require a planned migration and capability/RLS work; no migration is proposed or applied in F4.2.
