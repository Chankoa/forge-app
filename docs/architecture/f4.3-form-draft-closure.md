# F4.3 Form, Draft, And Layout Closure

## Lesson Draft

`LessonEditor` owns one controlled `LessonDraft` for title, summary, content, objectives, type, duration, and publishing status. Tabs render views of that same draft; no field relies on `defaultValue` or an independent tab state.

Forge Apply changes only this browser draft. It does not write to Supabase. Save serializes every draft field, calls `saveLessonAction`, and shows success only after that action resolves. The server validates the payload, updates the owned lesson, and revalidates course pages. A reload before Save restores persisted data; a reload after Save reads the updated data.

## Form And Upload Structure

The resource panel is a sibling of the lesson editor form, never a descendant. Its file picker and `type="button"` upload CTA construct an explicit `FormData` call to the server action. After strict extension validation, TXT always maps to `text/plain` and MD always maps to `text/markdown`. Because Supabase Storage uses a `File`/`Blob` body's intrinsic MIME instead of the upload option, the action rebuilds the body as a normalized `Blob`; browser-provided MIME values, including Windows `application/octet-stream`, are never sent to Storage.

Upload success means both private Storage upload and `course_sources` insertion succeeded. An insertion failure removes the uploaded object. On success, the resource list and Forge rail refresh through a local source-change event. PDF extraction remains deferred.

## F4.3a Upload Diagnosis

The verified backend contract uses the private `course-sources` bucket, whose policy checks the authenticated user path `{userId}/{courseId}/{uuid}-{filename}` through `can_author_source_path`. `course_sources` records use the same owner, course, path, normalized TXT/MD MIME type, UTF-8 extracted content, and `ready` status. The server uses the authenticated SSR client and never uses `service_role`.

Storage failures now have stable user messages for a missing bucket, an RLS/auth denial, and generic Storage failure. The server logs a bounded operational diagnostic with only the step, classification, status, Supabase message, bucket, logical path, and authenticated/owner booleans. It never logs credentials or document content. Database insertion failure triggers a Storage deletion attempt and reports a distinct source-insert failure; a failed rollback is logged separately.

The catalog audit verifies the intended bucket and policies but does not substitute for session RLS. The remaining browser smoke must use `test-forge.md`, observe the new classified result or success, and retain the corresponding safe server diagnostic as the definitive root-cause evidence.

## Sources And Rails

The Forge resolver remains the authorization and source-truth boundary: only usable selected text is injected, and only injected sources appear in `sourcesUsed`. The desktop workspace uses constrained 220-250px Structure and 280-320px Forge rails around a flexible editor. At 900px Forge moves below the editor grid; at 600px all workspace regions stack.

## Remaining Validation

Automated tests cover full draft serialization and existing Forge tests cover authorization, usable-source filtering, context injection, and truthful source attribution. Authenticated browser/provider smoke still depends on a shared authenticated browser session and configured AI environment.
